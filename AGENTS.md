## Workflow and validation
- The repository has a very large shared working tree; never stage broadly. Isolate ownership and stage only explicitly related files before committing.
- `summary_pattern_drift.py --json` must keep stdout as one JSON document; diagnostics such as the final verdict belong on stderr. `--json-out PATH` also enables JSON mode.
- Pattern drift compares the workflow merge pattern with `gen_repro_manifest.py`'s `ARTIFACT_JOBS` after exclusions; a real checkout may report drift from intentionally optional/missing artifacts, so resolve the contract before treating the result as a regression.
- The workflow contains multiple artifact download patterns; the pattern checker targets the `merge-multiple: true` block, so YAML formatting or block selection changes can affect the checker independently of artifact behavior.
- The existing `logs/` upload can carry `pattern_drift.json`; adding a separate CI artifact or manifest section is a separate contract decision, not implied by writing the sidecar.
- Focused validation used here: `python3 -m unittest _calisma.CIKTI.test_summary_pattern_drift`; broader related checks included `test_preview_server` and `test_colorize_rules`.
- The full `_calisma/CIKTI` unittest discovery is not a clean merge gate in this accumulated worktree: it includes generated fixtures and unrelated tests with known failures; use focused gates plus `verify_delivery.py --dir _calisma/CIKTI` for local signal.
- K21's synthetic ZIP determinism check is not evidence of PDF/TeXLive reproducibility; validate the real TeXLive/frozen-record path separately before treating K21 as authoritative.
- CI artifact ownership, workflow merge patterns, publish docs, and manifest generation are coupled contracts; changing one requires checking all four, especially for optional or advisory jobs.
- The smallest credible contract for the current verification work is the K21 SDE guard, summary CLI output modes, manifest provenance/combined hashes, and repack sidecar checks; test those entry points before broader discovery.
- K21 focused tests intentionally exercise both stable output and effective SDE input; the frozen-record gate is a separate filesystem-backed check and can fail even when the synthetic helper test passes.
- Mirror-coverage expected sets derive from the live filesystem (`os.listdir(github_scripts)` and zip sidecars), not `git ls-files`; any untracked file silently flips the expected set and breaks the gate in a fresh clone while staying green locally.
- Several committed verification contracts reference files never committed on any branch (generated `slides_z3/*.png`, `test_launchd_minimal_path.py`, some `github_scripts/*.js`). The mirror/plist gates pass locally only because those untracked files exist in this worktree; a clean checkout fails — reproduce on a fresh `git worktree` at HEAD before trusting a locally-green gate.
- `check_mirror_sync` searches hardcoded `~/Desktop/leibniz2` path candidates; its tests fail in isolated clones at other paths (e.g. `/tmp`) even though they pass in the real worktree, so treat that failure as location/environment, not a code regression.
- The repack step updates zips but does not maintain `cleanup_log.json`/`zip_lineage.json`; after any repack those records keep stale hashes and fail K14/lineage until the records are regenerated by hand.
- CI install steps for z3/lean/pdfinfo run after the unit-test step; when unit tests fail, the install steps are skipped and `--full` then reports environment-gap P0s that look like separate failures — diagnose upstream before chasing each red step.
- CI runs HEAD, not the working tree: a flag or script change present only as a staged/uncommitted edit (e.g. `audit_live_ci_sync.py --with-failure-pattern`) parses fine locally but fails in CI on the committed ref. Verify the committed ref, not the local tree.
- At commit time pre-commit stashes unstaged tracked edits into `~/.cache/pre-commit/patch*` and runs hooks on the staged-only tree; auto-editing hooks (README changelog sync) can collide with the reapply and orphan real edits. Rule: zero unstaged tracked delta before committing; the `check-precommit-orphans` gate flags residue — content-verify patches (reverse-check against the tree) before deleting them.
- Two auto-sync hooks own the test lists at commit time: `check_unit_tests.list` (battery, ~140 files, runs under `_calisma/.venv_z3` python) and the `HOOK_COVERAGE` map in `test_coverage_report.py`. Adding a test file needs no manual list edit; the coverage gate may fail once mid-staging (fail-closed by design) — re-run the commit.
- The commit-msg hook enforces a ≤72-char title per `.gitmessage`; long titles block the commit.
- Gitignored toolchains (`_calisma/.venv_z3`, `_calisma/pptx/node_modules`, `apps/dashboard-next/node_modules`) break fresh checkouts/worktrees at first commit with a module-import crash, not a test failure; `bash _calisma/dev_bootstrap.sh --check` (fail-closed) provisions/validates them — run it before trusting a fresh-worktree baseline.
- Port 8000 hosts Freebuff's own preview server (survives process reaping; serves `/api/latest`, `/api/trend`, `preview.html` with live data) — reuse it for dashboard E2E, never kill it.
- `/api/trend` ignores its `limit` query param by design (full-list contract, "same as /api/history"); consumers must window client-side (trend page: `slice(-20).reverse()`).
- The shellcheck gate (`shellcheck_hooks.sh`) lints an explicit HOOKS list only (verify_lean, commit_msg_hook, update_config_hook); new repo shell scripts are not auto-covered — add hook scripts to that list.
- Executed plan docs live in `docs/superpowers/plans/` and keep their checkboxes unchecked (repo convention even for completed plans).

## Tooling quirks
- Repository tools require structured object arguments: `read_files` takes a `paths` array; `str_replace` takes `path` plus replacement objects with explicit `oldString` and `newString`; malformed serialized arguments fail before execution.
- This environment exposes `run_terminal_command`, not legacy `run_command`/`run_command_placeholder`; use the listed tool names only.
- A registered Preview may lose its webview bridge after reload; `preview_snapshot` can still validate DOM/accessibility content, while screenshot/log calls may return `not_attached`/`no_webcontents` without implying a page code error.
- `register_preview` with `replace: true` can fail while releasing a healthy prior server; confirm the process and HTTP endpoint before restarting anything, since the error may be lifecycle/bridge state rather than an app crash.
- Orca/Pinokio/orchestration commands require their managed runtime; missing runtime metadata or control-plane connectivity is an environment limitation, not evidence that the repository launcher is broken.
- The SYNC terminal reaps all child/detached processes when the command ends (nohup/setsid die; `BACKGROUND` process_type is not implemented). Launch server+client inside one command block, or use the webapp-testing skill's `with_server.py` which manages lifecycle without reaping.
- The harness mangles apostrophes inside heredoc commit messages (shell parse error mid-message); write the message to a file (e.g. `/tmp/msg.txt`) and use `git commit -F`.
- File tools (`read_files`/`str_replace`/`write_file`) are blocked under gitignored paths like `.worktrees/`; use terminal (cat/sed/python) to read and edit those files instead.
- The 50-hook commit chain takes ~75-110s (check-unit-tests alone ~72s for ~140 files); give `git commit` runs a 300s+ timeout, or a timeout makes it look failed while HEAD is unchanged.
