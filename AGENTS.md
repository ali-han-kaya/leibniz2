# AGENTS.md

## Workflow and validation
- The repository has a very large shared working tree; never stage broadly. Isolate ownership and stage only explicitly related files before committing.
- `summary_pattern_drift.py --json` must keep stdout as one JSON document; diagnostics such as the final verdict belong on stderr. `--json-out PATH` also enables JSON mode.
- Pattern drift compares the workflow merge pattern with `gen_repro_manifest.py`'s `ARTIFACT_JOBS` after exclusions; a real checkout may report drift from intentionally optional/missing artifacts, so resolve the contract before treating the result as a regression.
- The workflow contains multiple artifact download patterns; the pattern checker targets the `merge-multiple: true` block, so YAML formatting or block selection changes can affect the checker independently of artifact behavior.
- The existing `logs/` upload can carry `pattern_drift.json`; adding a separate CI artifact or manifest section is a separate contract decision, not implied by writing the sidecar.
- Focused validation used here: `python3 -m unittest _calisma.CIKTI.test_summary_pattern_drift`; broader related checks included `test_preview_server` and `test_colorize_rules`.
- The full `_calisma/CIKTI` unittest discovery is not a clean merge gate in this accumulated worktree: it includes generated fixtures and unrelated tests with known failures; use focused gates plus `verify_delivery.py --dir _calisma/CIKTI` for local signal.
- K21's synthetic ZIP determinism check is not evidence of PDF/TeXLive reproducibility; validate the real TeXLive/frozen-record path separately before treating K21 as authoritative.
- CI artifact ownership, workflow merge patterns, publish docs, and manifest generation are coupled contracts; changing one requires checking all four, especially for optional or advisory jobs.
- The smallest credible contract for the current verification work is the K21 SDE guard, summary CLI output modes, manifest provenance/combined hashes, and repack sidecar checks; test those entry points before broader discovery.
- K21 focused tests intentionally exercise both stable output and effective SDE input; the frozen-record gate is a separate filesystem-backed check and can fail even when the synthetic helper test passes.
- Mirror-coverage expected sets derive from the live filesystem (`os.listdir(github_scripts)` and zip sidecars), not `git ls-files`; any untracked file silently flips the expected set and breaks the gate in a fresh clone while staying green locally.
- Several committed verification contracts reference files never committed on any branch (generated `slides_z3/*.png`, `test_launchd_minimal_path.py`, some `github_scripts/*.js`). The mirror/plist gates pass locally only because those untracked files exist in this worktree; a clean checkout fails — reproduce on a fresh `git worktree` at HEAD before trusting a locally-green gate.
- `check_mirror_sync` searches hardcoded `~/Desktop/leibniz2` path candidates; its tests fail in isolated clones at other paths (e.g. `/tmp`) even though they pass in the real worktree, so treat that failure as location/environment, not a code regression.
- The repack step updates zips but does not maintain `cleanup_log.json`/`zip_lineage.json`; after any repack those records keep stale hashes and fail K14/lineage until the records are regenerated by hand.
- CI install steps for z3/lean/pdfinfo run after the unit-test step; when unit tests fail, the install steps are skipped and `--full` then reports environment-gap P0s that look like separate failures — diagnose upstream before chasing each red step.
- CI runs HEAD, not the working tree: a flag or script change present only as a staged/uncommitted edit (e.g. `audit_live_ci_sync.py --with-failure-pattern`) parses fine locally but fails in CI on the committed ref. Verify the committed ref, not the local tree.
- At commit time pre-commit stashes unstaged tracked edits into `~/.cache/pre-commit/patch*` and runs hooks on the staged-only tree; auto-editing hooks (README changelog sync) can collide with the reapply and orphan real edits. Rule: zero unstaged tracked delta before committing; the `check-precommit-orphans` gate flags residue — content-verify patches (reverse-check against the tree) before deleting them. The gate prints a dedicated `BİLİNEN OLAY PARMAK-İZİ` block when an orphan's content matches the `recovery_patches_*` incident archive (sha256 exact + md5 digest for manual cross-check); an md5 match **without** a sha256 match is a separate `ZAYIF-PARMAK-İZİ ÇAKIŞMASI` warning and is **not** an incident label. Archiving does **not** clear the gate: the `KNOWN-INCIDENT` label is a warning, never an exemption — `main()` compares each patch's age to `WINDOW_HOURS = 24` regardless of label, so a >24h patch whose content already sits in `recovery_patches_*` still exits 1 (two tests pin `returncode == 1` for exactly this). The remedy the gate itself names is removing the residue from the cache. Prefer quarantine over deletion: prove byte-equality (sha256) with the archive first, then move the patches out (e.g. `~/.cache/pre-commit-orphans-quarantine-<date>/`) and keep a `MANIFEST.md` recording each file's digest and archive counterpart so the move is reversible. Never loosen the gate to make a commit pass. This rule is now **enforced**, not just documented: the `check-unstaged-delta` hook (first in the chain, `_calisma/CIKTI/check_unstaged_delta.py`) fails closed when an unstaged tracked delta exists, naming the files and the remedy. Do **not** "simplify" it to a plain `git diff --name-only` check — during a real `git commit` pre-commit's stash makes that always empty (proven: a mixed-tree commit landed green with the naive check), so the gate must also read this run's `patch<epoch>-<pid>` file, matched by **ancestor pid** (foreign/orphan patches in the same directory must stay ignored). `test_check_unstaged_delta.py::test_mixed_tree_commit_is_blocked_and_delta_survives` runs a real commit in a scratch repo and is the guard against pre-commit changing that mechanism.
- Long hook chains cannot be run in the foreground of a tool call: the full 59-hook run takes 7–10 min, and an over-running call gets its **whole process group killed** mid-chain (the log stops mid-line, the commit never lands, the index survives — a killed run did not strand a new patch). `nohup … &` is NOT enough; it stays in the same process group. Launch detached instead — `subprocess.Popen([...], start_new_session=True, stdin=subprocess.DEVNULL)` with `stdout` to a log file — then poll with short calls. Passing the message via `git commit -F <file>` also sidesteps heredoc/quoting damage on non-ASCII messages.
- Two auto-sync hooks own the test lists at commit time: `check_unit_tests.list` (battery, ~140 files, runs under `_calisma/.venv_z3` python) and the `HOOK_COVERAGE` map in `test_coverage_report.py`. Adding a test file needs no manual list edit; the coverage gate may fail once mid-staging (fail-closed by design) — re-run the commit.
- The commit-msg hook enforces a ≤72-char title per `.gitmessage`; long titles block the commit.
- Gitignored toolchains (`_calisma/.venv_z3`, `_calisma/pptx/node_modules`, `apps/dashboard-next/node_modules`) break fresh checkouts/worktrees at first commit with a module-import crash, not a test failure; `bash _calisma/dev_bootstrap.sh --check` (fail-closed) provisions/validates them — run it before trusting a fresh-worktree baseline.
- Port 8000 hosts Freebuff's own preview server (survives process reaping; serves `/api/latest`, `/api/trend`, `preview.html` with live data) — reuse it for dashboard E2E, never kill it.
- `/api/trend` honors `?limit=` **server-side** (this line used to say it ignored the param by design — that was wrong: the server silently dropped a documented contract while two live consumers were already sending it). Measured against the real CI artifact: 110,360 B unwindowed → 23,496 B at `?limit=20` (4.7× smaller), 5,095 B at `?limit=5`; the 8 kB mark is crossed at `limit=7`, not at 20. One window is applied to **both** halves (`history` + `refs_trend`'s row lists) because `preview.js` prints them side by side, and the clamped value is echoed in the body so a consumer can tell a windowed response from the whole artifact. Wiring gotcha: `HISTORY_PATH` lives under **preview-dir**, while `--dir` is only the `verify_delivery.py` root — the server refuses to start without that script.
- The shellcheck gate (`shellcheck_hooks.sh`) lints an explicit HOOKS list only (verify_lean, commit_msg_hook, update_config_hook); new repo shell scripts are not auto-covered — add hook scripts to that list.
- Executed plan docs live in `docs/superpowers/plans/` and keep their checkboxes unchecked (repo convention even for completed plans).
- **Measure every size/latency claim against real data, never a synthetic fixture.** The same code path measured 8 kB with hand-built 40-field rows and 23.5 kB with the actual `history.jsonl` records (1,619 B average) plus the CI `refs-trend.json` (75,778 B, retrievable with `gh run download`). A synthetic fixture is not a conservative estimate — it can be optimistic in either direction. Download the artifact before quoting a number. Corollary: a payload win is a *product* decision when the consumer's rendering depends on row count — the static pano still calls `/api/trend` without a limit, and `renderTrend` draws `rows.length` points with no cap, so bounding it would change a visible chart rather than just bytes.
- **A coverage record must name a job that exists and can actually run the test.** `CI_JOB_COVERAGE["dashboard-smoke"]` pointed at a job absent from `verify.yml` — a phantom record, the fail-open family (record present, execution absent), next to a render that printed PASS for an unresolvable ref. Related trap: the `verify` job *discovers* Playwright suites through `unittest discover` but `skipIf`s them, because Playwright is installed only in `a11y-gate`/`dashboard-next`. "Discovered by the runner" is not "executed by the runner".
- **Gate output that is piped to `/dev/null` cannot distinguish PASS from all-skip.** The unit-test hook discards each file's output, so a suite in which every test skipped looks byte-identical to a passing one. When a contract needs a browser, give the battery a static layer that runs in every environment: the file must be able to go red with no browser present.
- **A fixture can make its own assertion vacuous.** The live-stream snapshot emitted a constant `ts`, so "panel timestamp == newest trend row" was unfalsifiable; the `index % 10` stamp wrapped every 10 rows, so inside a 20-row window the row the test called "newest" was in fact the oldest — the fixture was hiding the very error being measured. Fixtures must be self-consistent with the contract they stand in for, and skewed data must be *monotonic*.
- **Green is not evidence: mutate before trusting a new assertion.** Every assertion added in this cycle was proven non-vacuous by breaking the implementation on purpose (limit 20→10, dropping `cache()`, `next/link`→raw `<a>`, removing `.reverse()`, `slice(-limit)`→`slice()`, dropping the refs-window call) and confirming red. Restore with `cp` from a saved copy and re-check `git status` — a mutation left behind is an undetected behavior change.
- **For "there are no files of type T" claims use `git ls-files`, never a filesystem scan.** A disk scan reports a false positive from `_calisma/.venv_z3/.../pre_commit/resources/empty_template_main.rs` (untracked vendor file) and from stray runtime trees; `git ls-files '*.rs'` is 0. Scans that walk `.venv`/`node_modules`/`.vercel` report the toolchain, not the repository.
- **An auto-sync hook cannot know a hash until after the commit it describes.** `check-changelog-sync` writes the commit's own hash into the changelog at commit time, so `--amend` immediately invalidates it and leaves a stale line that fails `test_gen_changelog`. Repair with `gen_changelog.py --prune` in a *separate* commit — amending re-creates the stale line on every attempt.
- **Classify a red test before fixing it.** A suite can pass alone and fail inside the full battery: `test_dashboard_keyboard_nav` passed 18/18 on its own (85.8 s) but failed in the 343 s run, and `check_tokens.py` carries a 10 s timeout that trips under load. Environment/time-budget failures and real regressions need opposite responses, and neither is a reason to reach for `--no-verify`.

## Tooling quirks
- Repository tools require structured object arguments: `read_files` takes a `paths` array; `str_replace` takes `path` plus replacement objects with explicit `oldString` and `newString`; malformed serialized arguments fail before execution.
- This environment exposes `run_terminal_command`, not legacy `run_command`/`run_command_placeholder`; use the listed tool names only.
- A registered Preview may lose its webview bridge after reload; `preview_snapshot` can still validate DOM/accessibility content, while screenshot/log calls may return `not_attached`/`no_webcontents` without implying a page code error.
- `register_preview` with `replace: true` can fail while releasing a healthy prior server; confirm the process and HTTP endpoint before restarting anything, since the error may be lifecycle/bridge state rather than an app crash.
- Orca/Pinokio/orchestration commands require their managed runtime; missing runtime metadata or control-plane connectivity is an environment limitation, not evidence that the repository launcher is broken.
- The SYNC terminal reaps all child/detached processes when the command ends (nohup/setsid die; `BACKGROUND` process_type is not implemented). Launch server+client inside one command block, or use the webapp-testing skill's `with_server.py` which manages lifecycle without reaping.
- The harness mangles apostrophes inside heredoc commit messages (shell parse error mid-message); write the message to a file (e.g. `/tmp/msg.txt`) and use `git commit -F`.
- File tools (`read_files`/`str_replace`/`write_file`) are blocked under gitignored paths like `.worktrees/`; use terminal (cat/sed/python) to read and edit those files instead.
- The commit chain is now 63 hooks and the unit-test battery alone runs ~345-370 s for 188 files (`make verify` ~6 min); give `git commit` runs a 600 s timeout, or a timeout looks like failure while HEAD is unchanged.
- **Renaming a path is not hiding it — a scanner that filters by name still sees it.** To reproduce a CI environment, *remove* what CI lacks: `check_skill_surfaces` globs every `package.json` and elides by directory name, so `node_modules.hidden-ci/**` was still scanned (1,708 files found) and produced failures that were artifacts of the method, not of the gate. Related: `trap ... EXIT` does **not** run when the harness SIGKILLs the process group at its hard timeout — a 600 s kill left 7 directories renamed and the server process alive. Use in-process `finally` with an inner time budget, and verify the restoration afterwards instead of trusting the trap.
- **`git rev-list X --not X` is degenerate** — the same ref on both sides of the exclusion yields plausible, meaningless counts, which is how one merge request produced three different answers (11, 9, 7) in three turns. Use `git rev-list <branch> --not <other-branch>`, and corroborate with `git rev-parse` before reporting a number.
